# Alerting and Detection Strategy (ADS) — Rule 100015

## Goal

Detect deletion of Volume Shadow Copies with vssadmin (T1490 Inhibit System Recovery). Ransomware commonly deletes local restore points right before encrypting, so the victim cannot roll back.

## Categorization

- **ATT&CK technique(s):** `T1490` — Inhibit System Recovery
- **Tactic(s) (v20):** Impact
- **Lab rule_id:** `100015`
- **Source Sigma rule:** `rules/sigma/T1490_vssadmin_delete_shadows.yml` (original, written for this lab)

## Strategy Abstract

Keys on Sysmon Event 1 where OriginalFileName is VSSADMIN.EXE and the command line contains delete shadows. It keys on the vssadmin process, not the cmd.exe launcher, so it fires once per command and also catches a renamed vssadmin.

## Technical Context

Chains on 61603. Fields used are `win.eventdata.originalFileName` and `win.eventdata.commandLine`. vssadmin delete shadows needs elevation, so the atomic runs elevated.

```xml
<!-- Rule 100015 - Volume shadow copy deletion via vssadmin -->
<!-- MITRE ATT&CK: T1490 - Inhibit System Recovery -->
<!-- Sysmon Event ID 1 - Process Creation -->
<!-- Converted from rules/sigma/T1490_vssadmin_delete_shadows.yml, then manual fixes (see ADS). -->
<rule id="100015" level="8">
  <if_sid>61603</if_sid>
  <field name="win.eventdata.originalFileName" type="pcre2">(?i)^VSSADMIN\.EXE$</field>
  <field name="win.eventdata.commandLine" type="pcre2">(?i)delete\s+shadows</field>
  <description>T1490: Volume shadow copy deletion - $(win.eventdata.commandLine)</description>
  <mitre>
    <id>T1490</id>
  </mitre>
</rule>
```

## Blind Spots and Assumptions

Other ways to remove or disable recovery evade: deleting `Win32_ShadowCopy` objects through PowerShell or CIM, `vssadmin resize shadowstorage`, `wbadmin delete catalog`, `bcdedit /set {default} recoveryenabled no`, and direct VSS API calls. The rule needs the words delete and shadows on the command line.

## False Positives

Bulk shadow deletion is rare on workstations, though backup tools and admins occasionally prune shadows. The baseline runs no vssadmin activity, so the FP cost of 0 across 5 runs (pass 0) is expected and does not test the rule against benign shadow maintenance.

## Validation

- **Positive test:** Atomic T1490 #1 "Windows - Delete Volume Shadow Copies" (GUID 43819286-91a9-4369-90ed-d31fb4da2c01): `vssadmin.exe delete shadows /all /quiet`, elevated.\
&emsp;*Result:* **Detected**, 3 lab runs.\
&emsp;*Latency (Sysmon event `systemTime` minus run start):* **1.941 s / 2.208 s / 3.169 s.**

- **Converter fidelity:** sigma_to_wazuh converted it (`rules/wazuh/T1490_sigma_to_wazuh.xml`).\
&emsp;*Manual fixes:* if_sid scoped to 61603, `delete\ shadows` widened to `delete\s+shadows` to allow any spacing, and MITRE IDs.\
&emsp;*Lab conventions:* rule ID, level 13 to 8.

- **Built-in comparison:** the stock run fired 92032 (level 3) on the vssadmin process and 92052 on the cmd launcher, both generic (T1059.003). No stock rule detects shadow copy deletion. In the lab runs 100015 outranked them at level 8.
- **Negative test:** FP cost 0 across 5 baseline runs (pass 0), precision 1.0.

## Priority

Suggested alert level: ***8*** as deployed in the lab. Given the impact, a production deployment would raise it to 12 or higher and alert immediately.

## Response

*Analyst Action:* Treat it as a likely ransomware precursor. Isolate the host, identify the parent process and account, and look for encryption activity and other recovery tampering (bcdedit, wbadmin) on the same host.
