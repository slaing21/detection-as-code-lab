# Alerting and Detection Strategy (ADS) — Rule 100010

## Goal

Detect local account and group discovery with net.exe and net1.exe (T1087.001). Listing local users and groups is an early post-compromise step an adversary uses to find accounts to abuse or target.

## Categorization

- **ATT&CK technique(s):** `T1087.001` — Account Discovery: Local Account
- **Tactic(s) (v20):** Discovery
- **Lab rule_id:** `100010`
- **Source Sigma rule:** `rules/sigma/T1087.001_net_account_discovery.yml` (original, written for this lab)

## Strategy Abstract

Keys on Sysmon Event 1 where the image is net.exe or net1.exe and the command line contains user or localgroup. net.exe starts net1.exe for these commands, so the rule matches both processes and fires twice per command.

## Technical Context

Hand written because sigma_to_wazuh did not produce a usable rule for the `all of selection_*` condition. Chains on 61603. Fields used are `win.eventdata.image` and `win.eventdata.commandLine`. The double fire (net.exe plus net1.exe) is why each malicious run raised 6 alerts for 3 net commands.

```xml
<!-- Rule 100010 - Local account/group enumeration via net.exe/net1.exe -->
<!-- MITRE ATT&CK: T1087.001 - Account Discovery: Local Account -->
<!-- Sysmon Event ID 1 - Process Creation -->
<!-- Hand written from rules/sigma/T1087.001_net_account_discovery.yml. (sigma_to_wazuh skips multi-selection conditions). -->
<rule id="100010" level="8">
  <if_sid>61603</if_sid>
  <field name="win.eventdata.image" type="pcre2">(?i)\\net1?\.exe$</field>
  <field name="win.eventdata.commandLine" type="pcre2">(?i)(user|localgroup)</field>
  <description>T1087.001: Local account enumeration - $(win.eventdata.image) $(win.eventdata.commandLine)</description>
  <mitre>
    <id>T1087.001</id>
  </mitre>
</rule>
```

## Blind Spots and Assumptions

Enumeration without net.exe evades: PowerShell `Get-LocalUser` and `Get-LocalGroupMember`, WMI queries of `Win32_UserAccount`, and direct API calls. The `user` match is unanchored, so it also matches `net use ... /user:...` commands. Those match rule 100012 as well (both level 8), and Wazuh raises one alert per event, so one of the two lab rules would be suppressed on that event and the pack could label lateral movement as account discovery.

## False Positives

Admins and scripts enumerate local accounts routinely. The baseline runs `net.exe user` and `net.exe localgroup` (manifest actions `enum-local-users` and `enum-local-groups`), and each produces a net.exe and a net1.exe event, so the rule raised 4 alerts per baseline run: FP cost 20 across 5 runs, the same in pass 0 and pass 1. Precision 0.13 as computed by `aggregate.py` (3 detected runs against 20 benign alerts).

## Tuning Decision

Tuning was not applied. The atomic runs `net user`, `net localgroup "Users"`, and `net localgroup`, and the baseline runs `net user` and `net localgroup`. The commands are the same, so the command line cannot separate them. The only difference is the parent process (cmd.exe from the atomic's command_prompt executor, powershell.exe from the baseline script), which is an artifact of the two harnesses, so filtering on it would game the baseline. Local account enumeration with net.exe is not separable from benign administration at the single-event level, so the rule stays at coverage 2 and the FP cost is reported as the finding. A volume fix exists that would not change the score: keying on net1.exe only would remove the double fire, cutting the malicious alerts from 6 to 3 per run and the FP cost from 20 to 10. Not applied, since it would need its own baseline pass and would leave the rule at coverage 2.

## Validation

- **Positive test:** Atomic T1087.001 (GUID 80887bec-5a9b-4efc-a81d-f83eb2eb32ab) "Enumerate all accounts (Local)": `net user`, `dir c:\Users\`, `cmdkey.exe /list`, `net localgroup "Users"`, `net localgroup`, command_prompt executor.\
&emsp;*Result:* **Detected**, 3 lab runs, 6 alerts per run.\
&emsp;*Latency (Sysmon event `systemTime` minus run start):* **0.650 s / 0.690 s / 0.647 s.**

- **Converter fidelity:** Not converted (see Technical Context). Written by hand from the Sigma logic and confirmed live with the atomic.
- **Built-in comparison:** the stock run fired 92031 ("Discovery activity executed"), which mapped the net user event to T1087, the parent technique, a correct attribution at the parent level. 92036 also fired on net.exe as a generic cmd-shell hit (T1059.003/T1574.001). In the lab runs 100010 outranked both at level 8 and refined the attribution to T1087.001.
- **Negative test:** FP cost 20 across 5 baseline runs (4 per run), the same in both passes.

## Priority

Suggested alert level: ***8***

## Response

*Analyst Action:* Check the parent process and user. Enumeration from an interactive admin shell is expected. Enumeration started by an Office app, a script host, a service account, or a web server process is escalated. With an FP cost of 20 over 5 baseline runs, in production this works better as a correlation input than as a standalone alert.
