# Alerting and Detection Strategy (ADS) — Rule 100006

## Goal

Detect the fodhelper.exe UAC bypass (T1548.002). An adversary writes a command under `HKCU\Software\Classes\ms-settings\shell\open\command`, then launches the auto-elevating fodhelper.exe, which runs that command at high integrity without a UAC prompt.

## Categorization

- **ATT&CK technique(s):** `T1548.002` — Abuse Elevation Control Mechanism: Bypass User Account Control
- **Tactic(s) (v20):** Privilege Escalation
- **Lab rule_id:** `100006`
- **Source Sigma rule:** `rules/sigma/T1548.002_uac_bypass_fodhelper.yml` (derived from SigmaHQ, `proc_creation_win_uac_bypass_fodhelper.yml` by E.M. Anhaus, oscd.community, "Bypass UAC via Fodhelper.exe")

## Strategy Abstract

Keys on Sysmon Event 1 where the parent image is fodhelper.exe. fodhelper.exe does not normally start child processes, so any child of it is the suspicious case, whatever that child is.

## Technical Context

Chains on 61603 and uses one field, `win.eventdata.parentImage`. The atomic never ran in this lab, so the rule was validated with a crafted event. `tools/craft_event.py` takes a captured Event 1 alert, sets the parent to fodhelper.exe and the image to cmd.exe, and prints the event as one JSON line for wazuh-logtest.

```xml
<!-- Rule 100006 - Child process spawned by fodhelper.exe (UAC bypass) -->
<!-- MITRE ATT&CK: T1548.002 - Abuse Elevation Control Mechanism: Bypass User Account Control -->
<!-- Sysmon Event ID 1 - Process Creation -->
<!-- Converted from rules/sigma/T1548.002_uac_bypass_fodhelper.yml with sigma_to_wazuh (raw output in rules/wazuh/), then manual fixes (see ADS). -->
<rule id="100006" level="10">
  <if_sid>61603</if_sid>
  <field name="win.eventdata.parentImage" type="pcre2">(?i)\\fodhelper\.exe$</field>
  <description>T1548.002: Child process spawned by fodhelper.exe (possible UAC bypass) - $(win.eventdata.image)</description>
  <mitre>
    <id>T1548.002</id>
  </mitre>
</rule>
```

## Blind Spots and Assumptions

Keys on one auto-elevating binary. UAC bypasses that use other auto-elevating binaries (computerdefaults.exe, sdclt.exe, eventvwr.exe, and others) evade. The setup step, the write to the ms-settings handler key (Sysmon Event 13), would catch the fodhelper variant even when the launch is blocked, but no rule on it was written or measured here. The rule assumes the payload is started directly by fodhelper.exe.

## False Positives

The upstream rule lists legitimate use of the Windows Features troubleshooter, but fodhelper.exe rarely starts a child in normal use. The rule was deployed during both baseline passes and raised 0 alerts. The baseline runs nothing involving fodhelper.exe, so that 0 says nothing about benign fodhelper use.

## Validation

Atomic blocked by Microsoft Defender (execution_failed). Rule 100006 deployed and logic-validated via wazuh-logtest against a crafted fodhelper-child Event 1 (fires as id 100006 at a raised level; transcript saved). At its production level 10 it is shadowed by built-in rule 92046 (level 12, T1548.002), which fired on the same event. Finding: T1548.002 is both prevented at the endpoint (Defender) and covered by stock SIEM rules at higher severity than the lab rule, so 100006 adds no coverage.

- **Positive test:** Atomic T1548.002 "Bypass UAC using Fodhelper" (GUID 58f641ea-12e3-499a-b684-44dee46bd182). Defender blocked it (Access is denied on process start) both elevated and non-elevated, so atomic_status is execution_failed, no telemetry was produced, and the technique is not scored (protocol §3). The technique was kept in the matrix rather than replaced because the block is itself a result and the rule was shadowed by stock 92046 in wazuh-logtest.\
&emsp;*Result:* **Blocked** on both attempts, recorded as one stock-state row in `results/runs.csv`.\
&emsp;*Latencies:* **Not Recorded** since it was blocked.

- **Converter fidelity:** sigma_to_wazuh converted it (`rules/wazuh/T1548.002_sigma_to_wazuh.xml`).\
&emsp;*Manual fixes:* if_sid scoped to 61603, the parentImage match anchored with `$`, and MITRE IDs.\
&emsp;*Lab conventions:* rule ID, level 13 to 10. `docs/transcripts/T1548.002-logtest.txt` shows both halves of the shadow: with 100006 at level 10 the event alerts as 92046 (level 12, T1548.002), and with 100006 temporarily raised to 13 it alerts as 100006.

- **Built-in comparison:** stock 92046 (level 12, T1548.002) fired on the same crafted event and shadows 100006 at its production level.
- **Negative test:** 0 alerts across both 5-run baseline passes.

## Priority

Suggested alert level: ***10*** (stock 92046 at level 12 is the alert an analyst would actually see)

## Response

*Analyst Action:* Confirm the child process and its command line, check `HKCU\Software\Classes\ms-settings\shell\open\command` for the planted value and remove it, and treat the host as compromised at high integrity.
