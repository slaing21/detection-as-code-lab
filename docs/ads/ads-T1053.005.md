# Alerting and Detection Strategy (ADS) — Rule 100002

## Goal

Detect scheduled task creation with `schtasks.exe /create` (T1053.005). An adversary registers a task that runs their payload on a schedule or trigger, which gives execution, persistence, and sometimes privilege escalation when the task runs as a more privileged account.

## Categorization

- **ATT&CK technique(s):** `T1053.005` — Scheduled Task/Job: Scheduled Task
- **Tactic(s) (v20):** Execution, Persistence, Privilege Escalation
- **Lab rule_id:** `100002`
- **Source Sigma rule:** `rules/sigma/T1053.005_schtasks_creation.yml` (derived from SigmaHQ, `proc_creation_win_schtasks_creation.yml` by Florian Roth (Nextron Systems), "Scheduled Task Creation Via Schtasks.EXE")

## Strategy Abstract

Keys on Sysmon Event 1 where the image is schtasks.exe and the command line contains /create, excluding tasks created by SYSTEM or NT AUTHORITY. Catches scheduled-task persistence created from the command line.

## Technical Context

Chains on 61603 (Sysmon Event 1). Fields used are `win.eventdata.image`, `win.eventdata.commandLine`, and `win.eventdata.user`. The account negate keeps the SigmaHQ filter values (`AUTHORI` and `AUTORI`), which cover NT AUTHORITY and its localized forms. The atomic also produced Event 11 (task file) and Event 13 (TaskCache registry write), but the rule does not use them. sysmon-modular does not log svchost's write of the TaskCache `Actions` value, so the task's command is only visible in the schtasks.exe command line.

```xml
<!-- Rule 100002 - Scheduled task created with schtasks.exe -->
<!-- MITRE ATT&CK: T1053.005 - Scheduled Task/Job: Scheduled Task -->
<!-- Sysmon Event ID 1 - Process Creation -->
<!-- Hand written from rules/sigma/T1053.005_schtasks_creation.yml. sigma_to_wazuh skipped it (unsupported "1 of" condition, see ADS). -->
<rule id="100002" level="6">
  <if_sid>61603</if_sid>
  <field name="win.eventdata.image" type="pcre2">(?i)\\schtasks\.exe$</field>
  <field name="win.eventdata.commandLine" type="pcre2">(?i)\ /create\ </field>
  <field name="win.eventdata.user" type="pcre2" negate="yes">(?i)AUTHORI|AUTORI</field>
  <description>T1053.005: Scheduled task created with schtasks.exe - $(win.eventdata.commandLine)</description>
  <mitre>
    <id>T1053.005</id>
  </mitre>
</rule>
```

## Blind Spots and Assumptions

Detects only schtasks.exe. Task creation through the PowerShell ScheduledTasks module (Register-ScheduledTask) or direct COM (ITaskService) spawns no schtasks.exe process and evades. The account negate also drops any adversary task created as SYSTEM.

## False Positives

schtasks /create is routine administration: maintenance jobs, installers, GPO. The baseline runs it once per run and it fired on every run in both passes, FP cost 5 of 5, precision 0.375.

## Tuning Decision

A tuning pass was assessed and rejected. The chosen atomic (42f53695) runs `SCHTASKS /Create /SC ONCE /TN spawn /TR C:\windows\system32\cmd.exe`. The benign baseline runs `schtasks /Create /TN LabBenignTask /TR "cmd.exe /c echo lab" /SC DAILY`. Both launch System32 cmd.exe, so there is no target-path discriminator. The only structural difference in the commands is the trigger, and tuning on it fails both ways. Narrowing to persistence triggers (ONLOGON, ONSTART) would miss this ONCE atomic and drop coverage to 1. Excluding DAILY would pass this baseline only because the baseline uses DAILY, and would not generalize, since malware using DAILY evades and benign ONCE tasks still fire. The parent process also differs (cmd.exe from the atomic's command_prompt executor, powershell.exe from the baseline script), but that is an artifact of the two harnesses, so filtering on it would game the baseline the same way. Command-line scheduled-task creation launching a system binary is not separable from benign administration at the single-event level, so the rule stays at coverage 2 and the FP cost is reported as the finding.

## Validation

- **Positive test:** Atomic T1053.005 "Scheduled task Local" (GUID 42f53695-ad4a-4546-abb6-7d837f644a71), `SCHTASKS /Create /SC ONCE /TN spawn /TR C:\windows\system32\cmd.exe /ST <time>` from the command_prompt executor.\
&emsp;*Result:* **Detected**, 3 lab runs. 100002 pre-empted stock 92032 on the same event.\
&emsp;*Latency (Sysmon event `systemTime` minus run start):* **0.831 s / 0.846 s / 0.833 s.**

- **Converter fidelity:** Not converted. sigma_to_wazuh skipped the source rule because of its `1 of filter_main_*` condition, so 100002 was written by hand from the Sigma logic, validated with wazuh-logtest, and confirmed live with the atomic. The upstream optional Office filter was not carried over (see the note in the Sigma file).
- **Built-in comparison:** the stock run's only alert was 92032 ("Suspicious Windows cmd shell execution", level 3, T1087/T1059.003), which fired because the atomic ran under cmd /c. No stock rule maps schtasks.exe task creation to T1053.005 (stock_attribution generic).
- **Negative test:** FP cost 5 across 5 baseline runs (1 per run, manifest action `task-register`) in pass 0, and the same in pass 1, where the rule was unchanged (repeatability check per protocol §7.1).

## Priority

Suggested alert level: ***6***

## Response

*Analyst Action:* Check the task name, trigger, run-as account, and /TR target. A task that runs a script or binary from a user-writable path, or that was created by an unexpected parent process, is escalated. A task that matches a known maintenance job is closed as benign. With an FP cost of 5 of 5 baseline runs, this rule works better as a correlation input than as a standalone alert in production.
