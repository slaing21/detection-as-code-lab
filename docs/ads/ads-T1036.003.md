# Alerting and Detection Strategy (ADS) — Rule 100007

## Goal

Detect execution of a renamed system utility (T1036.003). An adversary copies a trusted binary such as cmd.exe under another name so name-based detections and casual review miss it.

## Categorization

- **ATT&CK technique(s):** `T1036.003` — Masquerading: Rename Legitimate Utilities
- **Tactic(s) (v20):** Stealth
- **Lab rule_id:** `100007`
- **Source Sigma rule:** `rules/sigma/T1036.003_renamed_binary.yml` (derived from SigmaHQ, `proc_creation_win_renamed_binary.yml` by Matthew Green @mgreen27, Ecco, James Pemberton @4A616D6573, oscd.community, Andreas Hunkeler (@Karneades), "Potential Defense Evasion Via Binary Rename")

## Strategy Abstract

Keys on Sysmon Event 1 where OriginalFileName is a known system utility (cmd, net, 7z, wevtutil, and so on) but the Image path is not the matching binary name. A disagreement between the PE header name and the on-disk name is the signature of a renamed utility.

## Technical Context

Chains on 61603. Compares the PE header name (`win.eventdata.originalFileName`) against the on-disk name (`win.eventdata.image`). The atomic copied cmd.exe to `C:\Windows\Temp\lsass.exe`, so the event carries OriginalFileName `Cmd.Exe` and Image `C:\Windows\Temp\lsass.exe`, which the rule matches (see `docs/transcripts/T1036.003-logtest.txt`). Wazuh 4.14.7's built-in MITRE data still names T1036.003 "Rename System Utilities" under the "Defense Evasion" tactic (logtest output), so Wazuh's own tactic labels lag ATT&CK v20. sysmon-modular's RuleName on this event was `technique_id=T1083` (File and Directory Discovery), so the Sysmon annotation did not identify the technique either.

```xml
<!-- Rule 100007 - Renamed system utility (OriginalFileName vs Image mismatch) -->
<!-- MITRE ATT&CK: T1036.003 - Masquerading: Rename System Utilities -->
<!-- Sysmon Event ID 1 - Process Creation -->
<!-- Converted from rules/sigma/T1036.003_renamed_binary.yml with sigma_to_wazuh (raw output in rules/wazuh/), then manual fixes (see ADS). -->
<rule id="100007" level="8">
  <if_sid>61603</if_sid>
  <field name="win.eventdata.originalFileName" type="pcre2">(?i)^(Cmd\.Exe|CONHOST\.EXE|7z\.exe|7za\.exe|7zr\.exe|WinRAR\.exe|wevtutil\.exe|net\.exe|net1\.exe|netsh\.exe|InstallUtil\.exe)$</field>
  <field name="win.eventdata.image" type="pcre2" negate="yes">(?i)\\(cmd|conhost|7z|7za|7zr|winrar|wevtutil|net|net1|netsh|installutil)\.exe$</field>
  <description>T1036.003: Renamed system utility - OriginalFileName $(win.eventdata.originalFileName) running as $(win.eventdata.image)</description>
  <mitre>
    <id>T1036.003</id>
  </mitre>
</rule>
```

## Blind Spots and Assumptions

Catches only the fixed OriginalFileName list in the rule. A renamed utility outside that list evades, as does a recompiled binary whose PE OriginalFileName has been stripped or changed.

## False Positives

None observed. The baseline runs no renamed binaries, so FP cost is 0 across all 5 runs.

## Shadow Finding

In the deployed stack this rule never produces an alert. The chosen atomic (5ba5a3d1) renames a system utility, and its process-creation event is caught by stock Wazuh rule 61625, which outranks 100007 (level 8) and maps the event to T1055. All three malicious runs recorded detected=false, builtin_rule_id=61625, builtin_mitre_ids=T1055, stock_attribution=misattributed, coverage score 1. This is a finding on its own: out of the box Wazuh does not merely miss the rename, it actively mislabels it as process injection, and the accurate lab rule loses the single-alert race. Per evaluation-protocol §5 the lab rule is not raised above the stock rule, because suppressing a higher-severity stock alert to win attribution is the wrong trade and the misattribution is itself worth reporting.

The shadow depends on the name the atomic chose. 61625 fired because the copy was named lsass.exe, so a rename to a name no stock rule watches would likely leave 100007 as the top match. That variant was not measured. A proposed fix that stays within protocol §5 is a child rule chained on 61625 (`if_sid` 61625) that matches the same OriginalFileName and Image mismatch at level 12 or higher and tags T1036.003. Wazuh raises the most specific matching rule in the chain, so the alert would keep the stock severity and carry the correct technique, instead of suppressing the stock alert. Proposed, not measured.

## Validation

- **Positive test:** Atomic T1036.003 (GUID 5ba5a3d1-cf3c-4499-968a-a93155d1f717), upstream name "Masquerading as Windows LSASS process": `copy %SystemRoot%\System32\cmd.exe %SystemRoot%\Temp\lsass.exe`, then runs the copy with `/B`. Telemetry present (Event 1) on all 3 runs.\
&emsp;*Result:* **Not Detected** on all 3 runs, because 100007 was shadowed by 61625 (see Shadow Finding).\
&emsp;*Latency:* **Not recorded** since 100007 was shadowed by 61625.

- **Converter fidelity:** sigma_to_wazuh converted it (`rules/wazuh/T1036.003_sigma_to_wazuh.xml`) with the right logic, an OriginalFileName list plus 11 negated Image fields.\
&emsp;*Manual fixes:* if_sid scoped to 61603, the 11 negate fields consolidated into one alternation (same logic), and MITRE IDs.\
&emsp;*Lab conventions:* rule ID, level 10 to 8. `docs/transcripts/T1036.003-logtest.txt` shows both halves of the shadow: with 100007 at level 8 the event alerts as 61625 (level 12, T1055), and with 100007 temporarily raised to 13 it alerts as 100007.

- **Built-in comparison:** the stock run fired 61625 ("Sysmon - Suspicious Process - lsass", level 12) mapped to T1055 Process Injection, a misattribution.
- **Negative test:** 5-run baseline FP cost = **0**

## Priority

Suggested alert level: ***8***

## Response

*Analyst Action:* The stock rule shadows it in the deployed stack, the analyst sees the 61625 / T1055 alert, so the response note should read: a T1055 lsass-process alert raised on a renamed system utility is most likely masquerading (T1036.003), not injection.
