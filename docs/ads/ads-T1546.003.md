# Alerting and Detection Strategy (ADS) — Rule 100004

## Goal

Detect WMI event subscription persistence (T1546.003). An adversary registers an event filter, a consumer, and a binding between them, so WMI runs their command whenever the filter's condition is met. The subscription survives reboots and its command runs as SYSTEM.

## Categorization

- **ATT&CK technique(s):** `T1546.003` — Event Triggered Execution: Windows Management Instrumentation Event Subscription
- **Tactic(s) (v20):** Privilege Escalation, Persistence
- **Lab rule_id:** `100004`
- **Source Sigma rule:** `rules/sigma/T1546.003_wmi_event_subscription.yml` (derived from SigmaHQ, `sysmon_wmi_event_subscription.yml` by Tom Ueltschi (@c_APT_ure), "WMI Event Subscription")

## Strategy Abstract

Alerts on any Sysmon WMI event: Event 19 (WmiEventFilter), Event 20 (WmiEventConsumer), and Event 21 (WmiEventConsumerToFilter). The rule has no field conditions. Registering a permanent WMI subscription is rare in normal administration, so the registration itself is the signal.

## Technical Context

Event 20 always went to built-in 89501 (level 12), which shares the Event 20 parent rule (61648) with 100004 (level 8). Wazuh evaluated the higher-level sibling first, so 100004 never alerted on Event 20.

Chains on 61647, 61648, and 61649, the stock Sysmon base rules for Events 19, 20, and 21. Scoping to those base rules keeps the rule on the Sysmon channel. The description uses `win.eventdata.eventType` and `win.eventdata.operation` so the alert shows which part of the subscription was registered.

```xml
<!-- Rule 100004 - WMI event subscription created (filter, consumer, or binding) -->
<!-- MITRE ATT&CK: T1546.003 - Event Triggered Execution: Windows Management Instrumentation Event Subscription -->
<!-- Sysmon Event ID 19, 20, 21 - WmiEvent -->
<!-- Converted from rules/sigma/T1546.003 with sigma_to_wazuh (raw output in rules/wazuh/), then manual fixes (see ADS). -->
<rule id="100004" level="8">
  <if_sid>61647, 61648, 61649</if_sid>
  <description>T1546.003: WMI event subscription $(win.eventdata.eventType) $(win.eventdata.operation)</description>
  <mitre>
    <id>T1546.003</id>
  </mitre>
</rule>
```

## Blind Spots and Assumptions

Temporary (in-session) WMI event subscriptions are not persisted and Sysmon Events 19 to 21 do not record them, so they evade. The rule alerts when the subscription is registered, not when the consumer later runs its command. Because Event 20 goes to stock 89501 in this stack, the lab rule's own alerts cover only the filter and the binding (Events 19 and 21). The rule assumes Sysmon is logging WMI events, which the sysmon-modular config does.

## False Positives

Management, monitoring, and some vendor agents register permanent WMI subscriptions, so a real fleet would need an allowlist by filter or consumer name. The lab baseline creates no WMI subscription, so the measured FP cost of 0 across 5 runs (pass 0) is expected and says little about real-world noise.

## Validation

- **Positive test:** Atomic T1546.003 #1 "Persistence via WMI Event Subscription - CommandLineEventConsumer" (GUID 3c64f177-28e2-49eb-a799-d767b24dd1e0).\
&emsp;*Result:* **Detected**, 3 lab runs. 100004 fired on Events 19 and 21 in every run.\
&emsp;*Latencies (Sysmon event `systemTime` minus run start):* **1.448 s / 1.406 s / 1.208 s (Event 19).**

- **Converter fidelity:** sigma_to_wazuh converted it (`rules/wazuh/T1546.003_sigma_to_wazuh.xml`).\
&emsp;*Manual fixes:* if_sid scoped to the Sysmon WMI base rules 61647, 61648 and 61649 (the generic list plus an eventID regex would also match event IDs 19, 20 and 21 from other channels, such as Windows Update's System event 19), and MITRE IDs.\
&emsp;*Lab conventions:* rule ID, level 10 to 8.

- **Built-in comparison:** the stock run fired 89501 (level 12, T1546.003) on the Event 20 command line consumer, a correct attribution, and 92027 (level 4) on the child powershell.exe started by Invoke-AtomicTest. No stock rule fired on Events 19 or 21. In the lab runs 100004 and 89501 both alert, on different events, so the technique is covered twice.
- **Negative test:** FP cost 0 across 5 baseline runs (pass 0), precision 1.0.

## Priority

Suggested alert level: ***8*** (below stock 89501 at 12 by design, per protocol §5)

## Response

*Analyst Action:* List the subscriptions (`Get-CimInstance -Namespace root/subscription -ClassName __EventFilter`, then `CommandLineEventConsumer` and `__FilterToConsumerBinding`), read the consumer's command, and remove all three objects if they do not belong to a known agent. Treat an unknown CommandLineEventConsumer as confirmed persistence.
