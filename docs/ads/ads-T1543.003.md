# Alerting and Detection Strategy (ADS) — Rule 100005

## Goal

Detect Windows service creation with sc.exe (T1543.003). An adversary installs a service that runs their binary, which gives persistence across reboots and usually execution as SYSTEM.

## Categorization

- **ATT&CK technique(s):** `T1543.003` — Create or Modify System Process: Windows Service
- **Tactic(s) (v20):** Persistence, Privilege Escalation
- **Lab rule_id:** `100005`
- **Source Sigma rule:** `rules/sigma/T1543.003_sc_create_service.yml` (derived from SigmaHQ, `proc_creation_win_sc_create_service.yml` by Timur Zinniatullin, Daniil Yugoslavskiy, oscd.community, "New Service Creation Using Sc.EXE")

## Strategy Abstract

Keys on Sysmon Event 1 where the image is sc.exe and the command line contains both create and binpath, and the binPath value does not point into a trusted signed location. A service whose binary lives outside System32, SysWOW64, or Program Files is the suspicious case.

## Technical Context

Chains on 61603. The binPath negate is scoped to the value after binpath= so the sc.exe path itself does not trip it, and it uses ["\\]* before the drive letter to absorb the escaped quote and doubled backslashes the eventchannel decoder emits.

```xml
<!-- Rule 100005 - Windows service created with sc.exe -->
<!-- MITRE ATT&CK: T1543.003 - Create or Modify System Process: Windows Service -->
<!-- Sysmon Event ID 1 - Process Creation -->
<!-- tuning_pass 1: negate binPath into System32/SysWOW64/Program Files to drop benign service FPs. ["\\]* absorbs the escaped quote and doubled backslashes the eventchannel decoder emits (logtest's json decoder does not, see ADS). -->
<rule id="100005" level="6">
  <if_sid>61603</if_sid>
  <field name="win.eventdata.image" type="pcre2">(?i)\\sc\.exe$</field>
  <field name="win.eventdata.commandLine" type="pcre2">(?i)^(?=.*create)(?=.*binpath)</field>
  <field name="win.eventdata.commandLine" type="pcre2" negate="yes">(?i)binpath=\s*["\\]*[a-z]:\\+(Windows\\+System32|Windows\\+SysWOW64|Program Files)</field>
  <description>T1543.003: Windows service created with sc.exe - $(win.eventdata.commandLine)</description>
  <mitre>
    <id>T1543.003</id>
  </mitre>
</rule>
```

## Blind Spots and Assumptions

Same trusted-location bypass as 100003. Catches only service creation via sc.exe, not the PowerShell service cmdlets, the ChangeServiceConfig API, or direct registry writes under Services.

## False Positives

Admins and installers create services, usually pointing at Program Files or System32. The baseline creates a service with binPath C:\Windows\System32\cmd.exe. Pass 0 FP cost 5, pass 1 FP cost 0.

## Validation

- **Positive test:** Atomic T1543.003 "Service Installation CMD" (GUID 981e2942-e433-44e9-afc1-8c957a1496b6), elevated: `sc.exe create AtomicTestService_CMD binPath= "<atomics>\T1543.003\bin\AtomicService.exe" start=auto type=Own`, then `sc.exe start`. The binPath points into the atomics folder, outside the trusted locations, so the tuned rule still fires.\
&emsp;*Result:* **Detected** on all 3 pass-1 lab runs at level 6.\
&emsp;*Latencies (Sysmon event `systemTime` minus run start):* *pass 0:* **0.815 s / 0.818 s / 0.831 s,** *pass 1:* **0.708 s / 0.674 s / 0.784 s.**

- **Converter fidelity:** sigma_to_wazuh converted it (`rules/wazuh/T1543.003_sigma_to_wazuh.xml`).\
&emsp;*Manual fixes:* if_sid scoped to 61603 (the converter used the generic Windows parent list), the sc.exe image match anchored with `$` (the converter turned Sigma `endswith` into contains), the two command-line fields combined into one lookahead pattern that still requires both create and binpath (same logic), and MITRE IDs.\
&emsp;*Lab conventions:* rule ID, level 7 to 6. Tuning pass 1 added the binPath negate, which passed wazuh-logtest on the json path before it matched the escaped form the live eventchannel decoder produces (see research-notes).\
&emsp;*Regex filter:* the converter does not translate the Sigma `|re` modifier. The regenerated output escapes the trusted-location pattern as literal text with wildcards and puts it on `full_log`, so it never matches and the converted rule fires on every sc.exe create with a binPath. The deployed negate was written by hand in tuning pass 1.

- **Built-in comparison:** the stock run fired 92307 (level 3, T1543.003) on the services.exe ImagePath registry write and 61138 (level 5, T1543.003) on System event 7045, both correct attributions. 92032 fired on sc.exe create and start because of the cmd /c parent. In the lab runs 100005 pre-empted 92032 on the sc.exe create event while 92307 and 61138 still fired on their own events.
- **Negative test:** pass-1 baseline FP cost 0. That is runs b6 to b10, precision 1.0. Pass 0, before the negate, was FP cost 5 (manifest action `service-create`).

## Priority

Suggested alert level: ***6***

## Response

*Analyst Action:* Check the service name, binPath, start type, and run-as account. A binary outside Program Files or System32, an auto-start service created from a script, or an unsigned binary is escalated. Stop and delete the service and preserve the binary for analysis if it is unexpected.
