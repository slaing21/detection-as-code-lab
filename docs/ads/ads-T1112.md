# Alerting and Detection Strategy (ADS) — Rule 100009

## Goal

Detect the registry change that disables UAC remote restrictions (T1112 Modify Registry). Setting `LocalAccountTokenFilterPolicy` to 1 gives local administrator accounts a full administrative token over the network, which lets an adversary use remote admin tools and move laterally with local credentials.

## Categorization

- **ATT&CK technique(s):** `T1112` — Modify Registry
- **Tactic(s) (v20):** Defense Impairment, Persistence
- **Lab rule_id:** `100009`
- **Source Sigma rule:** `rules/sigma/T1112_localaccounttokenfilterpolicy.yml` (original, written for this lab)

## Strategy Abstract

Keys on Sysmon Event 13 (registry value set) where the target object ends in LocalAccountTokenFilterPolicy and the value data is 1. Matching the enabling value keeps the rule quiet when the value is removed or set back to 0.

## Technical Context

Chains on 61615 (Sysmon Event 13). Fields used are `win.eventdata.targetObject` and `win.eventdata.details`. The rule keys on the value name rather than the full key path, which survives the doubled backslashes the eventchannel decoder emits (see research-notes). Sysmon writes DWORD data as `DWORD (0x00000001)`, which the details regex matches. sysmon-modular's RuleName tagged this event T1548.002. That is a Sysmon annotation, not a Wazuh alert, and it names a different technique than the one under test.

```xml
<!-- Rule 100009 - UAC remote restrictions disabled (LocalAccountTokenFilterPolicy = 1) -->
<!-- MITRE ATT&CK: T1112 - Modify Registry -->
<!-- Sysmon Event ID 13 - Registry value set -->
<!-- Converted from rules/sigma/T1112_localaccounttokenfilterpolicy.yml with sigma_to_wazuh, then manual fixes (see ADS). -->
<rule id="100009" level="8">
  <if_sid>61615</if_sid>
  <field name="win.eventdata.targetObject" type="pcre2">(?i)LocalAccountTokenFilterPolicy$</field>
  <field name="win.eventdata.details" type="pcre2">(?i)\(0x0*1\)$</field>
  <description>T1112: UAC remote restrictions disabled - LocalAccountTokenFilterPolicy set to $(win.eventdata.details)</description>
  <mitre>
    <id>T1112</id>
  </mitre>
</rule>
```

## Blind Spots and Assumptions

Covers one registry value out of the many that T1112 includes, so this is a narrow detection of one high-value change, not coverage of registry modification in general. It depends on the Sysmon config logging this value, which sysmon-modular does. Changes written while Sysmon is stopped, or to an offline hive, evade.

## False Positives

Admin tooling that deliberately enables remote administration with local accounts sets this value. The baseline writes only an HKCU Run key, which the rule does not match, so the FP cost of 0 across 5 runs (pass 0) reflects the rule's narrow scope. The technique matrix predicted high FP risk for T1112 because it assumed a broad registry rule. Keying on one value removed that risk at the cost of coverage.

## Validation

- **Positive test:** Atomic T1112 (GUID e8c7c404-b669-4cf9-bafd-fdad89a5bbb1), upstream name "Disable UAC remote restrictions via LocalAccountTokenFilterPolicy": `Set-ItemProperty -Path "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System" -Name "LocalAccountTokenFilterPolicy" -Type DWord -Value 1 -Force`, PowerShell executor, elevated.\
&emsp;*Result:* **Detected**, 3 lab runs.\
&emsp;*Latency (Sysmon event `systemTime` minus run start):* **1.244 s / 1.034 s / 2.368 s.**

- **Converter fidelity:** sigma_to_wazuh converted it (`rules/wazuh/T1112_sigma_to_wazuh.xml`).\
&emsp;*Manual fixes:* if_sid scoped to 61615 (Event 13) instead of the generic Windows list, the targetObject match anchored with `$` (the converter turned Sigma `endswith` into contains), the details match changed from `\(0x00000001\)` to `\(0x0*1\)$`, and MITRE IDs (the converter copies the Sigma tags into `<mitre>`).\
&emsp;*Lab conventions:* rule ID, level 13 to 8.

- **Built-in comparison:** no stock rule fired on the stock run (stock_attribution none). This is net-new coverage.
- **Negative test:** FP cost 0 across 5 baseline runs (pass 0), precision 1.0.

## Priority

Suggested alert level: ***8***

## Response

*Analyst Action:* Confirm which process wrote the value and under which account, set it back to 0 or remove it if no approved tool needs it, and review network logons with local accounts that followed the change.
