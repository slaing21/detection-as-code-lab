# Alerting and Detection Strategy (ADS) — Rule 100011

## Goal

Detect system information discovery with systeminfo.exe (T1082). An adversary runs it to learn the OS version, patch level, domain membership, and hardware of a host they have compromised.

## Categorization

- **ATT&CK technique(s):** `T1082` — System Information Discovery
- **Tactic(s) (v20):** Discovery
- **Lab rule_id:** `100011`
- **Source Sigma rule:** `rules/sigma/T1082_systeminfo_execution.yml` (derived from SigmaHQ, `proc_creation_win_systeminfo_execution.yml` by frack113, "Suspicious Execution of Systeminfo")

## Strategy Abstract

Keys on Sysmon Event 1 where OriginalFileName is sysinfo.exe, the PE name of systeminfo.exe. Matching the PE name instead of the path catches both the normal binary and a renamed copy.

## Technical Context

Chains on 61603 and uses one field, `win.eventdata.originalFileName`. The Sigma source matches Image ending in `\systeminfo.exe` OR OriginalFileName `sysinfo.exe`. sigma_to_wazuh put both fields into one rule, which turns that OR into an AND. The deployed rule keeps only the OriginalFileName branch, which restores the intended logic for both the normal and the renamed binary.

```xml
<!-- Rule 100011 - System information discovery with systeminfo.exe -->
<!-- MITRE ATT&CK: T1082 - System Information Discovery -->
<!-- Sysmon Event ID 1 - Process Creation -->
<!-- Converted from rules/sigma/T1082_systeminfo_execution.yml with sigma_to_wazuh (raw output in rules/wazuh/), then manual fixes (see ADS). -->
<rule id="100011" level="6">
  <if_sid>61603</if_sid>
  <field name="win.eventdata.originalFileName" type="pcre2">(?i)^sysinfo\.exe$</field>
  <description>T1082: System information discovery with systeminfo.exe - $(win.eventdata.commandLine)</description>
  <mitre>
    <id>T1082</id>
  </mitre>
</rule>
```

## Blind Spots and Assumptions

Other ways to collect the same information evade, for example PowerShell `Get-ComputerInfo` or `Get-CimInstance Win32_OperatingSystem`, `ver`, and registry queries. The atomic's second command (`reg query HKLM\SYSTEM\CurrentControlSet\Services\Disk\Enum`, a virtualization check) is not covered by this rule.

## False Positives

systeminfo is common in admin scripts and inventory tools. The baseline runs `systeminfo.exe` once per run (manifest action `systeminfo`), so the rule fired on every baseline run: FP cost 5 across 5 runs in both passes, precision 0.375.

## Tuning Decision

Tuning was not applied. The atomic and the baseline both run systeminfo.exe with no arguments. The only difference is the parent process (cmd.exe from the atomic's command_prompt executor, powershell.exe from the baseline script), which is an artifact of the two harnesses, so filtering on it would game the baseline. A single systeminfo execution carries no malicious signal of its own, so the rule stays at coverage 2 and the FP cost is reported as the finding.

## Validation

- **Positive test:** Atomic T1082 #1 "System Information Discovery" (GUID 66703791-c902-4560-8770-42b8a91f7667): `systeminfo` and `reg query HKLM\SYSTEM\CurrentControlSet\Services\Disk\Enum`, command_prompt executor.\
&emsp;*Result:* **Detected**, 3 lab runs, matched by OriginalFileName.\
&emsp;*Latency (Sysmon event `systemTime` minus run start):* **0.967 s / 0.920 s / 0.911 s.**

- **Converter fidelity:** sigma_to_wazuh converted it (`rules/wazuh/T1082_sigma_to_wazuh.xml`) but ANDed the two Sigma OR branches (see Technical Context).\
&emsp;*Manual fixes:* dropped the Image branch to restore the intended logic, if_sid scoped to 61603, and MITRE IDs.\
&emsp;*Lab conventions:* rule ID, level 7 to 6.

- **Built-in comparison:** the stock run fired only 92032 (level 3, T1087/T1059.003) because the atomic ran under cmd /c. No stock rule maps systeminfo to T1082 (stock_attribution generic). In the lab runs 100011 pre-empted 92032.
- **Negative test:** FP cost 5 across 5 baseline runs (1 per run), the same in both passes.

## Priority 

Suggested alert level: ***6***

## Response

*Analyst Action:* Check the parent process and user. systeminfo from an interactive admin session is expected. systeminfo started by a script host, an Office app, a service, or next to other discovery commands is escalated. On its own this is a low-value signal that works better as a correlation input.
