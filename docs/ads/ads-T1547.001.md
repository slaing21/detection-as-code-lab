# Alerting and Detection Strategy (ADS) — Rule 100003

## Goal

To detect logon persistence via a Run-key write (T1547.001): an adversary adding a value under HKCU/HKLM ...\CurrentVersion\Run so their payload runs at the next logon. This rule alerts on the write.

## Categorization

- **ATT&CK technique(s):** `T1547.001` — Registry Run Keys / Startup Folder
- **Tactic(s) (v20):** Persistence, Privilege Escalation
- **Lab rule_id:** `100003`
- **Source Sigma rule:** `rules/sigma/T1547.001_registry_run_keys.yml` (derived from SigmaHQ, `registry_set_asep_reg_keys_modification_currentversion.yml` by Victor Sergeev, Daniil Yugoslavskiy, Gleb Sukhodolskiy, Timur Zinniatullin, oscd.community, Tim Shelton, frack113 (split), "CurrentVersion Autorun Keys Modification")

## Strategy Abstract

Keys on Sysmon Event 13 where the target object is a CurrentVersion\Run key and the value data does not point into a trusted signed location (System32, SysWOW64, Program Files). An autostart entry pointing outside those is the suspicious case.

## Technical Context

Chains on both 61615 and 92300. 92300 is the parent that fires in the live eventchannel pipeline, 61615 is the one logtest’s json decoder reaches, so chaining on both makes the rule testable and production-correct. Explicit Run-key targetObject match, negate on details.

```xml
<!-- Rule 100003 - Registry Run key persistence -->
<!-- MITRE ATT&CK: T1547.001 - Boot or Logon Autostart Execution: Registry Run Keys -->
<!-- Sysmon Event ID 13 - Registry Value Set -->
<!-- tuning_pass 1: chained on 61615 (logtest/json path) and 92300 (production/eventchannel path), explicit Run-key match, negate value data in trusted dirs to drop benign autostart FPs (see ADS). -->
<rule id="100003" level="10">
  <if_sid>61615,92300</if_sid>
  <field name="win.eventdata.targetObject" type="pcre2">(?i)\\+CurrentVersion\\+Run</field>
  <field name="win.eventdata.details" type="pcre2" negate="yes">(?i)\\+(System32|SysWOW64|Program Files)\\+</field>
  <description>T1547.001: Registry Run key persistence - $(win.eventdata.targetObject) -> $(win.eventdata.details)</description>
  <mitre>
    <id>T1547.001</id>
  </mitre>
</rule>
```

## Blind Spots and Assumptions

The trusted-location negate is bypassable: an adversary who writes a payload into System32 or Program Files (requires privilege) or names a folder with a trusted token evades. Catches only the Run key family, not other ASEP locations such as the Startup folder, Winlogon, or services. The targetObject regex has no separator after `Run`, so RunOnce and RunServices writes also match. The Sigma source requires `\Run\` and does not match them. Detects the write, not the payload running at the next logon.

## False Positives

The baseline admin activity writes a Run key with `New-ItemProperty`, so 100003 fires on it. This is the expected FP that drives the score to 2. Installers and software write Run keys, nearly always into Program Files or System32, which the negate excludes. The baseline writes HKCU Run = C:\Windows\System32\notepad.exe. Pass 0 (no negate) FP cost 5, pass 1 (tuned) FP cost 0. The negate requires a separator right after the folder name, so `C:\Program Files (x86)\` is not excluded, and 32-bit software that writes a Run key there would still alert. Rule 100005's binPath negate does exclude Program Files (x86), so the two tuned rules treat it differently.

## Validation

- **Positive test:** Atomic T1547.001 "Reg Key Run" (GUID e55be3fd-3521-4610-9d1a-e210e42dcf05), `REG ADD "HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" /V "Atomic Red Team" /t REG_SZ /F /D "C:\Path\AtomicRedTeam.exe"`. The value data points outside the trusted locations, so the tuned rule still fires. 
&emsp;*Result:* **Detected** on all 3 pass-1 lab runs.\
&emsp;*Latencies (Sysmon event `systemTime` minus run start):* *pass 0:* **0.76s / 0.90s / 0.92s,** *pass 1:* **0.71s / 1.20s / 0.85s.**

- **Converter fidelity:** Not converted. 100003 was written by hand and chained under the stock Sysmon registry rules (see the note above). The tuned rule was verified with wazuh-logtest on the json path and live on the eventchannel path, since the two decoders present the fields differently (see research-notes).
- **Built-in comparison:** stock 92302 detects the reg.exe variant but is silent on the PowerShell variant (gap test: New-ItemProperty write, no stock alert, 100003 fired).
- **Negative test:** baseline FP cost = **0** (pass 1, runs b6 to b10). Pass 0, before the negate, was FP cost 5 (manifest action `runkey-write`). Precision 1.0 after tuning.

## Priority

Suggested alert level: ***10***

## Response

*Analyst Action:* Confirm the Run value's target binary and the writing process, pull the binary if unexpected.
